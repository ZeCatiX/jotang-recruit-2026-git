# 趁热打铁：7 个问题的回答

所有数字都来自本仓库实际跑出来的结果（`task1_main.py` / `experiments.py`），
不是教材抄来的。环境：PyTorch 2.11.0+cpu，`make_moons(300, noise=0.2)`，
种子 `SEED=0`，模型默认 `2→64→64→2`（4,482 参数）。

## 1. 激活函数应该选什么？为什么？

**结论：选 ReLU 或 ELU，别用 sigmoid。**

`experiments.py` 里固定 2 层 × 64、Adam lr=1e-3、150 epoch，只换激活函数：

| 激活函数 | 测试准确率 | 验证损失 | 训练准确率 |
|---|---|---|---|
| ReLU | 1.000 | 0.2124 | 0.995 |
| tanh | 1.000 | 0.2253 | 0.986 |
| **sigmoid** | **0.867** | **0.4513** | **0.857** |
| ELU | 1.000 | **0.1617** | 0.986 |

**为什么 sigmoid 差这么多？** 因为它的梯度上限是 `σ(z)(1-σ(z)) ≤ 0.25`。
网络的梯度要靠链式法则逐层相乘传回前面：

```
∂L/∂w_1 = ∂L/∂z_2 · w_2 · σ'(z_1)
```

每一层都要乘上一个 ≤0.25 的因子。2 层是 0.0625，10 层就是 `0.25^10 ≈ 9.5e-7`——
梯度指数级衰减，前面几层几乎收不到学习信号，这就是**梯度消失**。
本任务只有 2 层就已经把测试准确率从 100% 打到 86.7%，再深下去肯定更糟。

**tanh 为什么也比 ReLU 差点意思？** tanh 把「饱和区间居中」的问题解决了
（0 附近梯度是 1，不是 0.25），但它的输出仍以 0 为中心、梯度上限只有 1，
而且所有输出都被压进 (-1,1)——深层网络里照样要连乘。
从上面的表能看到 tanh 的验证损失（0.2253）比 ReLU（0.2124）略高。

**ELU 反而是四个里验证损失最低的（0.1617，比 ReLU 低 24%）。**
ReLU 有个「死神经元」问题：如果某个神经元在某次更新后偏置变成很大的负数，
它就永远输出 0，梯度也永远是 0，这个神经元彻底废掉了。
ELU 在 `x < 0` 时给一个很小的负梯度（`α·e^x`，默认 α=1），
神经元还能被拉回来。代价是输出无界、计算稍微慢一点。

**工程上的选择顺序**：ReLU / LeakyReLU / ELU 随便挑一个，先用 ReLU；
只有当明确观察到「死神经元」（大量神经元梯度恒为 0）时才考虑 ELU。
**sigmoid 现在只用在输出层**（二分类要算概率时），不当隐藏层激活。

## 2. 损失函数应该选什么？为什么？如果改成三分类怎么办？

**结论：分类任务用 `CrossEntropyLoss`。**

我这里是二分类，用的是：

```python
crit = torch.nn.CrossEntropyLoss()
loss = crit(logits, y)     # logits 是「未归一化」的输出
```

**三个关键点：**

**(1) 它内部自带 softmax，所以喂的是 logits，不是概率。**
`CrossEntropyLoss` = `LogSoftmax` + `NLLLoss`。如果我手动先 `softmax()` 再喂进去，
等于做了两次 softmax，结果就错了。这是新手最常踩的坑。
本任务里 `MLP` 最后一层是 `nn.Linear(prev, output_dim)` 后面**不加**激活函数，
就是为了直接输出 logits。

**(2) 它比「先 softmax 再手写 NLL」数值上稳定。**
`LogSoftmax` 内部会先减去 `max(z)` 再取 exp，避免 `exp` 溢出。
对比一下我 task0 里亲手写的朴素版：`np.exp(np.array([-800.]))` 会直接
`overflow encountered in exp`，而 `torch.softmax` / `LogSoftmax` 毫无压力。

**(3) 它的梯度有个漂亮的简化形式。**
对 softmax + cross entropy，可以证明：

```
∂L/∂z_c = p_c - 1{y = c}
```

也就是「预测概率减 one-hot 真值」。我在 task0 的 `hello_ml.py` 里用
`logits=[2.0, 1.0, 0.1], y=1` 验算过：`dL/dz = [0.659, -0.758, 0.099]`，
正好等于 `p - one_hot(y)`，完全对上。
这个形式意味着：**预测对了就减小梯度，预测错了就反向修正**，没有额外的系数，
梯度量纲干净、不会因为概率太接近 0 或 1 而爆炸。

**如果换成三分类怎么办？**

几乎什么都不用改——这正是 `CrossEntropyLoss` 设计得好用的地方：

| 要改的地方 | 怎么改 |
|---|---|
| 数据 | `y` 的标签从 `{0,1}` 变成 `{0,1,2}`（300 条按三类分层划分） |
| 模型最后一层 | `nn.Linear(prev, 2)` → `nn.Linear(prev, 3)` |
| 损失函数 | **不变**，`CrossEntropyLoss()` 直接支持任意类数 |
| 评估 | `argmax` 还是 `argmax`，准确率公式不变 |

具体到本仓库，把 `common.py::MLP` 的 `output_dim` 默认值从 2 改成 3 就行，
`train_model` 和 `evaluate` 一行都不用动。

**但要注意三分类引入的两个新问题：**

1. **混淆矩阵变成 3×3**，「总准确率」的信息量进一步下降。
   比如模型永远猜最多的那一类，三类各占 1/3 时准确率也有 33%，看着像蒙的
   但其实连蒙都不如。必须看**每个类的 recall / precision / F1**，
   或者宏平均 F1（`f1_score(..., average='macro')`）。
2. **类别不平衡的风险变大**。两类时 90/10 已经很难受了，三类时 80/10/10
   或者 60/30/10 会让小类基本学不到。`class_weight` 的算法也要跟着改：
   每个类的权重取 `n_total / (n_classes * n_c)`，而不是现在的
   `n_total / (2 * n_c)`。

## 3. `zero_grad()`、`backward()`、`step()` 分别干什么？不清梯度会怎样？

标准的 mini-batch 循环是：

```python
for x_batch, y_batch in loader:
    opt.zero_grad()          # ① 清空上一步攒下的梯度
    loss = crit(model(x_batch), y_batch)
    loss.backward()         # ② 反向传播，算出本批的梯度
    opt.step()              # ③ 用梯度更新参数：w ← w - lr·g
```

**① `zero_grad()`** — 把每个参数的 `.grad` 归零。
PyTorch 的梯度是**累加**的：`backward()` 会把新梯度**加到**已有的 `.grad` 上，
不是覆盖。所以每个 epoch 开始前必须手动清零，不然上一步的梯度会一直残留。

**② `backward()`** — 从 loss 出发，用反向模式自动微分，
按链式法则把梯度算出来写到每个 `requires_grad=True` 的张量的 `.grad` 上。
比如我模型里 4,482 个参数，`backward()` 后这 4,482 个数都有了对应的梯度。

**③ `step()`** — 按 `w ← w - lr · g`（SGD）或者 Adam 的自适应公式更新参数。
注意这一步**不会**清除梯度，所以循环回到开头要靠 `zero_grad()` 清。

---

**不清梯度会怎样？我实测了，结果比教科书上写的有意思：**

写了一个可开关的循环（`clear=False` 就跳过 `zero_grad()`），跑主数据集：

| 优化器 | lr | epoch | 清梯度？ | 测试损失 | 最终梯度范数 |
|---|---|---|---|---|---|
| Adam | 1e-3 | 150 | 是 | 0.018 | 5.49e-01 |
| Adam | 1e-3 | 150 | **否** | 0.034 | 5.38e+01（×98） |
| Adam | 1e-3 | 2000 | 是 | 0.018 | 7.15e-01 |
| Adam | 1e-3 | 2000 | **否** | 0.001 | 2.74e+02（×380） |
| SGD | 1e-2 | 150 | 是 | 0.094 | 3.44e-01 |
| SGD | 1e-2 | 150 | **否** | 0.062 | 2.47e+01（×72） |
| SGD | 1e-2 | 2000 | 是 | 0.015 | 8.09e-01 |
| SGD | 1e-2 | 2000 | **否** | **5.371** ← 崩了 | 1.05e+02 |
| SGD | 1e-1 | 500 | 是 | 0.011 | 1.51e-01 |
| SGD | 1e-1 | 500 | **否** | **1.155** ← 崩了 | 8.26e+00 |

**三个观察：**

1. **梯度确实像理论上说的那样无限累积**：范数从 0.55 一路涨到 273，涨了两百倍。
   因为每个 epoch 的 `backward()` 都往同一个 `.grad` 上加，
   第 k 次 `step()` 用的是前 k 个 epoch 梯度的总和。

2. **SGD 会崩**：2000 epoch 时测试损失从 0.015（正常）恶化到 5.371，
   完全学废了。原因是累积梯度方向一致 → 每一步的有效步长被放大几十倍 →
   早就越过最优点开始震荡发散。

3. **Adam 居然活了下来**，2000 epoch 不 clear 的测试损失甚至只有 0.001。
   这是**因为 Adam 会自适应归一化**：它的更新量是 `lr · m̂ / (√v̂ + ε)`，
   分子（一阶动量）和分母（二阶动量的平方根）会**一起**随梯度膨胀而膨胀，
   比值近似不变，于是「有效步长」被强行压回 `lr` 附近，掩盖了梯度爆炸的问题。

**所以结论是**：不清梯度**一定**是 bug（梯度是错的），
但它会不会表现出来，取决于优化器。SGD 会立刻崩，
Adam/AdamW 这种自适应优化器可能几十轮都看不出来。
这是个很危险的 bug——**你以为训练正常，其实参数一直沿着累加的历史梯度走**。

## 4. 更深、更宽一定更好吗？过简单、过复杂各有什么问题？

**结论：不是。本任务里「更深更宽」的收益在很早期就消失了，成本却一直涨。**

`experiments.py` 的宽度实验（其他全部锁定）：

| 宽度 | 参数 | 测试准确率 | 验证损失 | 耗时 |
|---|---|---|---|---|
| 16 | 354 | 0.956 | 0.1768 | 0.93s |
| 32 | 1,218 | 1.000 | 0.1650 | 0.89s |
| 64 | 4,482 | 1.000 | 0.2124 | 1.11s |
| 128 | 17,154 | 1.000 | 0.2961 | 1.15s |
| 256 | 67,074 | 1.000 | **0.3850** | 1.67s |

层数实验：

| 层数 | 参数 | 测试准确率 | 验证损失 |
|---|---|---|---|
| 1 | 322 | 0.978 | 0.1980 |
| 2 | 4,482 | 1.000 | 0.2124 |
| 3 | 8,642 | 0.978 | 0.3808 |
| 4 | 12,802 | 1.000 | 0.4228 |
| 6 | 21,122 | 1.000 | 0.3091 |

**两个要点：**

1. **测试准确率撞到 1.000 的天花板后，「更大」看起来毫无损失。**
   宽度 32 到 256 四个配置准确率完全一样。
   但**验证损失**从 0.2124 涨到 0.3850（×1.8），说明更大的网络在训练集上拟合得更紧、
   泛化余量更小，只是 45 条测试集还没暴露出来。
   代价是真金白银：参数量 ×189（354 → 67,074），耗时 ×1.8。
   **宽 64 就是性价比最高点，再加没有任何好处。**

2. **层数也一样。** 2 层就到 1.000 了，3/4/6 层全在 97.8%~100% 晃，
   验证损失反而从 0.2124 升到 0.4228，参数堆到 65 倍。

**过简单（欠拟合）的问题：** 模型的表达能力不够，连训练集都拟合不好。
宽度 16 时训练准确率只有 0.967、测试 0.956，验证损失 0.1768——
它不是「没记住」，而是结构上就画不出正确的边界形状。
**训练损失本身就很低不了**，这是欠拟合最可靠的信号
（过拟合是训练损失很低但验证损失很高）。

**过复杂（过拟合）的问题：** 模型记住了训练集的噪声而不是规律。
我用 60 条数据（噪声 0.6）实测，4 层 × 256、198,658 参数的模型：
训练准确率 0.944、验证 0.667，**差距 +0.278**；
同样配置加 dropout 0.2 + 权重衰减 1e-2，差距压回 +0.111。
而且**四个模型的测试准确率全是 0.667**——单看准确率根本看不出过拟合，
必须看训练/验证差距。

**所以答案分三层：**

- 数据少、任务简单（本任务就是这样）：**够用就好**，大模型只会拖慢并增加过拟合风险
- 数据多、任务复杂（图像分类、NLP）：大模型能真正学到更精细的规律，
  这时候「更大」确实「更好」——**前提是你有足够的训练数据去喂它**
- 判断标准永远是**训练/验证差距**和**验证损失**，不是测试准确率

一句话：**模型复杂度应该和数据量、任务难度匹配，而不是越大越好。**

## 5. 学习率过大、过小分别怎么影响训练？loss 曲线有什么现象？

**结论：两端都坏，但坏法完全不同——而且「过大」这种坏法只看准确率会漏掉。**

固定 Adam、2 层 × 64、150 epoch，只改 lr：

| lr | 测试准确率 | 验证损失 | 验证准确率 | 训练耗时 |
|---|---|---|---|---|
| 1e-4 | **0.911** | 0.3387 | 0.844 | 1.23s |
| 3e-4 | 1.000 | **0.1521** ← 最低 | 0.956 | 1.43s |
| 1e-3 | 1.000 | 0.2124 | 0.956 | 1.40s |
| 3e-3 | 0.978 | 0.3776 | 0.933 | 1.76s |
| 1e-2 | 1.000 | 0.4107 | 0.956 | 1.35s |

**过小（1e-4）**：步子太小，`w ← w - lr·g` 每步挪得极近。
150 epoch 根本走不到最优区域——测试准确率 0.911，验证损失还停在 0.3387。
`fig6_学习率对比.png` 上能看到它的 loss 曲线**下降很慢、还在稳稳地往下走**，
没有波动。这是「还在学但没学完」的典型形状。

**过大（1e-2）**：**这里有个反直觉的发现——测试准确率照样 1.000！**
但验证损失冲到 0.4107，是甜点 3e-4（0.1521）的 **2.7 倍**。
这就是「在最优点附近来回震荡」：每一步都跨过头，然后又跨回来，
模型一直在最优解附近弹跳，从没真正停下来。
loss 曲线的形状是**锯齿状上下抖动**，或者干脆**发散成 NaN**。

**为什么准确率没掉？** 因为 45 条测试集的分类任务里，
即使模型参数在最优解附近晃，它的**决策方向**大体还是对的，
预测标签不变，准确率就还是 1.000。
**验证损失**才反映参数的实际位置——它诚实得多。
所以**只看准确率会漏掉「学习率过大」这种失败模式，必须同时看 loss 曲线**。

**甜点在哪？** 3e-4，验证损失 0.1521 全场最低。
有趣的是 1e-3 和 3e-3 只差 3 倍，验证损失从 0.2124 跳到 0.3776，
3e-3 甚至让测试准确率掉到 0.978——**说明这个任务在 1e-3 附近已经比较敏感了**。
教材常说「学习率差 3~5 倍内结果差不多」，在这里只有一半是对的。

**工程建议：**
1. 先用对数网格扫一遍（`1e-4, 3e-4, 1e-3, 3e-3, 1e-2` 就是我用的），
   **看验证损失而不是准确率**
2. 想更省事可以用 `torch.optim.lr_scheduler.OneReduceLR` 之类自动衰减
3. 大模型 + 大数据通常需要更小的 lr 和 warmup 阶段，
   因为参数多、梯度方向不稳定，步子大了直接发散

## 6. 类别不均衡会怎样？构造一个数据集试试

**结论：准确率会骗人，必须换指标；而且「模型偷懒猜多数类」是一个真实存在的诱惑。**

数据集是我手造的，不是 `make_moons`——为了让两类真正**重叠**：

```python
rng = np.random.RandomState(SEED)
X = np.vstack([
    rng.normal(loc=[-1.0, -1.0], scale=0.35, size=(900, 2)),  # 负类：紧、小
    rng.normal(loc=[-0.4, -0.4], scale=1.1,  size=(100, 2)),  # 正类：散、大、和负类重叠
])
y = np.concatenate([np.zeros(900), np.ones(100)])
```

**这里有个关键的设计考量**：如果正类放在 `[-1,-1]` 而负类放在 `[1,1]`
（两个高斯团离得远远的），模型不加权也能拿 100%，**根本不体现不均衡的问题**。
所以正类必须和负类大面积重叠，让「全猜多数类」成为一个有诱惑力的懒惰方案。

结果（测试集 150 条，90/10）：

| 方案 | 总准确率 | 正类召回 | 正类精度 | 正类 F1 | 混淆矩阵 |
|---|---|---|---|---|---|
| 平凡基线：全猜多数类 | 0.900 | **0.000** | 0.000 | 0.000 | `[[135,0],[15,0]]` |
| 直接训练（不加权） | **0.947** | 0.467 | 1.000 | 0.636 | `[[135,0],[8,7]]` |
| 加权训练（正类 5.0×） | 0.920 | **0.733** | 0.579 | **0.647** | `[[127,8],[4,11]]` |

**四个要点：**

**(1) 平凡基线的准确率就有 0.900。**
这意味着一个**完全不训练**的模型都能拿 90 分——那训练出来的 94.7% 只有 4.7 个百分点的增益。
**评估不均衡数据集时，第一个动作应该是算「全猜多数类」的基线**，
没有超过它多少百分点，这个模型就没什么价值。

**(2) 准确率说「不加权更好」，F1 说「加权更好」——两个指标吵起来了。**
不加权 0.947 vs 加权 0.920（准确率）；加权 0.647 vs 不加权 0.636（F1）。
原因是加权把分类阈值往正类方向推了：
代价是 8 个负类被误判成正类（精度从 1.000 掉到 0.579），
换来了多找回 5 个真正的正类（召回 0.467 → 0.733）。
**该信哪个取决于业务**：如果是「找病灶/找欺诈」这种漏掉一个代价极高的场景，
选加权（召回优先）；如果是「垃圾邮件过滤」这种误判代价高的场景，
选不加权（精度优先）。

**(3) 加权怎么加？** 用的是 `CrossEntropyLoss(weight=)`，
每个类的权重取 `n_total / (n_classes * n_c)`：

```python
w = torch.tensor([len(y)/(2*n_neg), len(y)/(2*n_pos)])   # = [0.556, 5.0]
crit = nn.CrossEntropyLoss(weight=w)
```

含义是「让每个类对总损失的贡献相等」。
不加权时，占 90% 的负类主导了损失梯度，模型自然优先把负类分对，
正类的 100 个样本被淹没在噪声里——**所以不加权时正类召回只有 46.7%**。

**(4) 除了加权，还有几种办法**（这次没做，但知道有）：
- **过采样正类**（SMOTE 之类）：数据量小、成本低
- **欠采样负类**：会丢信息，慎用
- **调决策阈值**：把 0.5 改成 0.3，把更多样本判成正类——这次实验里加权训练
  其实就是自动地做了这件事
- **换损失函数**：focal loss 专门针对「已经分对的样本不再算损失」，
  天然抑制多数类的主导
- **直接用适合不均衡的指标**：AUC-ROC、PR-AUC（比 ROC 更适合极不均衡）

## 7. 怎么人为制造过拟合？怎么判断过拟合？实现一下

**结论：三要素（小数据 + 大模型 + 长训练）；判断靠「训练/验证差距」和「验证损失」，不靠测试准确率。**

**制造过拟合的三要素，缺一不可：**

1. **数据要少**：60 条（36 条训练）。
2. **数据噪声要非零**：`noise=0.6`。**这个是最容易被忽略的一点。**
   如果 `noise=0`，月牙数据天然可分，哪怕 20 万参数的模型在验证集上也能拿满分，
   根本造不出差距——我第一次跑就是 `noise=0.0`，结果差距是 `+0.000`，实验彻底失败。
   噪声让「记住这 36 个点」和「猜对新样本」变成两件不同的事。
3. **模型要大、且无正则、且训练时间长**：4 层 × 256、198,658 参数、200 epoch、
   无 dropout、无权重衰减。

**怎么判断？看三个信号，按可靠性排序：**

| 信号 | 本任务实测 | 可靠性 |
|---|---|---|
| **训练/验证准确率差距持续拉大** | +0.083 → +0.222 → +0.278 | 最可靠 |
| **训练损失继续降，验证损失先降后升** | 训练 0.944 但验证损失一直上爬 | 很可靠，能定位拐点 |
| 测试准确率 | 四个模型**全是 0.667** | **不可靠！会骗人** |

第三个是重点：**过拟合的模型测试准确率常常没问题**（因为测试集是从同一个
分布采的，噪声样本也可能碰巧落在「正确」一侧）。
小测试集还会把误差量化吞掉（45 条集最小分辨率 2.2%）。

**实验结果**（`fig8_过拟合曲线.png`）：

| 配置 | 训练 | 验证 | **差距** | 测试 | 参数 |
|---|---|---|---|---|---|
| 太小：1 层 × 16 | 0.833 | 0.750 | +0.083 | 0.667 | 82 |
| 常规：2 层 × 64 | 0.889 | 0.667 | +0.222 | 0.667 | 4,482 |
| **过大：4 层 × 256，无正则** | 0.944 | 0.667 | **+0.278** | 0.667 | 198,658 |
| 过大 + dropout 0.2 + wd 1e-2 | 0.861 | 0.750 | +0.111 | 0.667 | 198,658 |

**三个观察：**

1. **差距随容量单调变宽**（+0.083 → +0.222 → +0.278）——这是过拟合最干净的一次性演示。
2. **加正则把差距压回 +0.111**，代价是训练准确率从 0.944 掉到 0.861，
   但验证准确率从 0.667 **升回 0.750**。这就是正则的全部意义：
   牺牲训练集拟合度换泛化能力。
3. **四个模型的测试准确率全是 0.667**——如果我只看这一列，会得出
   「模型大小无所谓」的错误结论。

**决策边界的可视化是最直观的证据**（`fig9_过拟合决策边界.png`）：
1 层 × 16 的模型边界几乎是一条直线（因为容量不够，画不出复杂形状）；
4 层 × 256 的模型边界**扭曲得非常厉害**，右边甚至挖出一个孤立的小口袋
只为了套住一两个训练点——这些点周围明明全是另一类的样本。
**这就是过拟合在几何上的样子：边界为了迎合每一个训练点而变得又绕又碎。**

**常用的缓解手段**（按我这次验证过的顺序）：

| 手段 | 效果 | 说明 |
|---|---|---|
| 增加数据量 | 最有效 | 但往往不可控 |
| **dropout** | 有效 | 训练时随机丢弃神经元，强迫模型不依赖单个神经元 |
| **权重衰减（L2 正则）** | 有效 | 惩罚大权重，让边界更平滑 |
| Early stopping | 有效 | 验证损失开始回升就停，靠耐心而不是正则 |
| 减少模型容量 | 有效 | 但要先知道「够不够」，容易欠拟合 |

dropout 和权重衰减这次同时用了（0.2 + 1e-2），差距从 +0.278 压到 +0.111，
但**没有单独消融**——所以不能说是哪个在起作用。如果要严格回答「哪个更有效」，
得再跑一次只开 dropout、一次只开权重衰减的对照。

## 附：本任务里我踩的坑

1. **`torch.manual_seed_all()` 在 2.11.0 被移除了**，直接调用抛 `AttributeError`。
   现在的 `torch.manual_seed()` 已经会给所有设备播种。用 `hasattr` 兼容。
2. **第一次过拟合实验用了 `noise=0.0`，结果差距 `+0.000`**，
   模型在验证集上也拿满分——实验设计错误，不是代码错误。
   换成 `noise=0.6` 才有区分度。**设计实验前先想清楚「怎么才算失败」**。
3. **第一次不均衡实验把正类放在 `[-1,-1]`、负类放在 `[1,1]`，
   不加权也 100%**——两个高斯团离得太远，重叠度为 0，
   不均衡的问题根本体现不出来。改成让两类分布大面积重叠才有效。
4. **`ctypes` 调 `GetCurrentProcess()` 必须显式声明 `restype = c_void_p`**，
   否则默认按 32 位 `c_int` 截断 64 位句柄，后续调用**静默失败返回 `nan`**，
   报错信息完全指向别处。
5. **`reshape(xx.shape)` 少了最后一维**：softmax 输出是 `(N, C)`，
   要 reshape 成 `(H, W, C)` 得写 `reshape(xx.shape + (-1,))`，
   直接 `reshape(xx.shape)` 会报 `ValueError: cannot reshape array of size 320000 into shape (400, 400)`。
6. **对照实验不加预热跑，内存数据会骗人**：第一个配置（width=16）会背上
   70 MiB 的分配器一次性开销，看起来「小模型反而更占内存」。
   加一次预热跑后所有增量都回到 ±3 MiB 的正常范围。
